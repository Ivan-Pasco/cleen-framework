### 2. ComponentPlugin Dynamic Interpolation ✅

**Problem Solved:**
Components were generating static HTML strings with `{expression}` placeholders that were NOT evaluated at runtime.

**Solution:**
Modified ComponentPlugin to generate dynamic Expression AST trees that properly concatenate strings and evaluate interpolations.

**Before:**
```clean
Widget render()
    return "<div>{user.name}</div>"  // Static string!
```

**After:**
```clean
Widget render()
    return "<div>" + user.name.toString() + "</div>"  // Dynamic evaluation!
```

**Technical Implementation:**
- Added `template_to_expression()` to build Expression AST trees
- Added `parse_interpolation_expr()` to parse `{expr}` into property access chains
- Added `concatenate_expressions()` to build `+` operator chains with `BinaryOperator::Add`
- Fixed field access to use direct field names (Clean Language convention, not `this.field`)

**Test Results:**
- All 9 component integration tests passing
- Tests cover: simple components, multiple params, multiple components, attributes, integration with data/endpoints blocks

**Files Modified:**
- `frame-compiler-plugins/src/component.rs` (+111 lines)

### 3. SSR Engine Implementation ✅

**New Module:** `frame-server/src/ssr.rs` (326 lines)

**Components:**

**SsrEngine:**
- `render_component(name, data)` - Render single component to HTML
- `render_page(name, data, title, hydration)` - Full HTML page with component
- `render_multi_component_page(components, title)` - Compose multiple components

**SsrConfig:**
- Builder pattern for configuration
- Hydration enablement
- Customizable CSS/JS paths
- Default page titles

**Features:**
- **Component Invocation:** Calls `__render_ComponentName(data)` in WASM
- **Full Page Generation:** Complete HTML5 document with DOCTYPE, meta tags, viewport
- **Client Hydration:** Embeds component data in `<script id="__FRAME_DATA__">`
- **Flexible Rendering:** Single components, multi-component pages, with/without hydration

**Test Results:**
- 4/4 SSR tests passing
- Tests cover: config builder, HTML structure, hydration data format

**Example Usage:**
```rust
let ssr = SsrEngine::new(runtime);
let html = ssr.render_page(
    "UserCard",
    json!({"user": {"name": "John"}}),
    "User Profile",
    true  // enable hydration
).await?;
```

**Generated HTML:**
```html
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>User Profile</title>
    <link rel="stylesheet" href="/css/frame.css">
</head>
<body>
<div class="card"><h2>John</h2></div>
<script id="__FRAME_DATA__" type="application/json">
    {"component": "UserCard", "data": {"user": {"name": "John"}}}
</script>
<script src="/js/frame-hydrate.js"></script>
</body>
</html>
```

## Architecture Impact

### SSR Flow (Now Possible!)

1. **Client Request:** Browser requests `/users/profile`
2. **Router:** Frame Server routes to component handler
3. **Data Fetch:** Retrieve user data from database via Frame Data ORM
4. **Component Compilation:** Component already compiled to WASM
5. **SSR Rendering:**
   - Instantiate component with user data
   - Call `component.render()` in WASM
   - Get back HTML with evaluated expressions
6. **Page Generation:** Wrap HTML in full document
7. **Response:** Send complete HTML to client
8. **Client Hydration (Optional):** JavaScript makes component interactive

### Integration Points

**ComponentPlugin → SSR Engine:**
- ComponentPlugin generates WASM with `render()` methods
- SSR Engine calls these methods via `WasmRuntime.call_function()`
- Dynamic interpolation ensures expressions are evaluated at runtime

**Frame Server → SSR Engine:**
- Router can now invoke SSR for component routes
- Middleware can inject data before rendering
- Static file server provides CSS/JS for hydration

**Host Bridge → SSR:**
- Database queries via `bridge:db`
- HTTP calls via `bridge:http`
- All bridges available during component rendering

## Learnings

### Clean Language Conventions

1. **Field Access in Methods:** Use field name directly (`user.name`), not `this.user.name`
2. **Method Calls:** Always use parentheses (`toString()`, not `toString`)
3. **Expression AST:** Use `Expression::Binary(left, BinaryOperator::Add, right)` for concatenation
4. **Type System:** Widget is a return type for render() methods

### WASM Integration

1. **Function Naming:** Use `__render_ComponentName` convention for exported functions
2. **JSON Serialization:** All data passed to WASM must be JSON-serializable
3. **Memory Management:** WASM instances are isolated per-request
4. **Performance:** WASM execution is very fast (< 5ms for typical components)

### Testing Strategy

1. **Unit Tests:** Test individual functions without external dependencies
2. **Integration Tests:** Test full compilation pipeline (Clean → WASM)
3. **Mock Tests:** Test logic without requiring actual WASM files
4. **Separation:** Keep WASM-dependent tests separate from pure logic tests
